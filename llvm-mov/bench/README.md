# bench — llvm-mov vs movfuscator vs native clang / rustc

Side-by-side ELF comparison of two mov-only backends (llvm-mov and
movfuscator) plus a 4-column native-clang reference (`-O0`..`-O3`) on
shared C and Rust source. Results live in [`results.md`](results.md),
regenerated by [`run.sh`](run.sh) and committed for diffability
across PRs and CI.

## Columns

Each fixture's table reports 7 columns:

| column | toolchain | what it measures |
|---|---|---|
| `llvm-mov` | clang IR → `llvm-mov-llc` → `as --32` → `ld` | mov-only via the stage-7 legalize |
| `movfuscator` | `movcc` (LCC + mov-only x86) | mov-only via the LCC-era approach |
| `clang -O0..-O3` | clang → `as --32` → `ld` | ordinary 32-bit native ELF at four opt levels |

Every column uses the same `_start.s` + `int 0x80` exit runtime
(no glibc, no dynamic loader), so the only thing differing between
columns is `main`'s body — making the comparison apples-to-apples.

The Rust fixtures use `rustc -C opt-level=0..3` in place of the
clang columns; the movfuscator column there is `—` (movcc is a
C-only frontend).

## Fixtures

| fixture          | source                                  | stage / shape exercised |
|------------------|-----------------------------------------|-----------|
| `return0` / `return42` | `movfuscator-wasm/tests/fixtures/` | trivial floor; runtime is process-exit dominated |
| `eq42`           | `bench/fixtures/`                       | 7c2 (CMP+Jcc EQ/NE) |
| `lt_unsigned`    | `bench/fixtures/`                       | 7c3 (unsigned predicates JB/JAE/JBE/JA) |
| `bitops`         | `bench/fixtures/`                       | 7b1 (AND/OR/XOR byte tables) |
| `sum10`          | `movfuscator-wasm/tests/fixtures/`      | 7a (ADD chain) + 7c4 (signed `jl`) loop |
| `fib10`          | `bench/fixtures/`                       | 7a + 7c1 dispatcher + 7c4 signed cmp loop |
| `shifts`         | `bench/fixtures/`                       | 7b2 imm shifts |
| `fib_rec`        | `bench/fixtures/`                       | 7d1 + 7d3 recursion (`fib(24)` — compute-bound, the only fixture whose runtime row carries meaningful signal) |
| `multi_call`     | `bench/fixtures/`                       | 7d3 multiple sequential CALLs |
| `rust_main`         | `examples/rust/main/`          | Rust trivial through `llvm-mov-llc` (no deps) |
| `rust_fib`          | `examples/rust/fib/`           | Rust recursion (`fib(24)`) through `llvm-mov-llc` (no deps) |
| `rust_png_header`   | `examples/rust/png_header/`    | PNG signature + IHDR parse via `read_unaligned::<u32>` (no deps) |
| `rust_jpeg_header`  | `examples/rust/jpeg_header/`   | JPEG SOI/SOF0 marker walk (no deps) |
| `rust_bmp_decode`   | `examples/rust/bmp_decode/`    | Full 32bpp BMP decode (no deps) |
| `rust_base64_decode`| `examples/rust/base64_decode/` | `base64 = "0.22"` decode "Hello, World!" — **hybrid** (user mov + crate native) |
| `rust_qoi_decode`   | `examples/rust/qoi_decode/`    | `qoi = "0.4"` 2x2 RGBA decode — **hybrid** |

The "hybrid" rows are the honest baseline for how much of a
deps-using Rust ELF the backend currently mov-ifies: user-crate
`.text` (`*_main`, panic shim, and any decoder logic written *in*
this crate) goes through `llvm-mov-llc`, but each crates.io dep's
code is pulled in as the native i686 `.o` rustc compiled it to. The
mov ratio for those rows is therefore strictly below 100 % even when
the user code is fully mov-only — see
[issue #11](https://github.com/sksat/x86.mov/issues/11) for the
roadmap on getting deps through `llvm-mov-llc` too.

Fixtures live in either `bench/fixtures/` (llvm-mov-specific) or the
shared `../movfuscator-wasm/tests/fixtures/`. The runner searches
`bench/fixtures/` first so an llvm-mov-side override takes precedence.

## Metrics

| metric | how |
|---|---|
| total ELF (bytes) | `stat -c %s` on the linked file |
| `.text` size | sum of `objdump -h` Size column for `.text*` |
| `.rodata` size | sum of `objdump -h` Size column for `.rodata*` |
| mov count / total | `objdump -d -Mintel` of `.text`, mnemonic column |
| non-mov mnemonics | what's still in `.text` outside the mov family |
| wall-clock runtime | `hyperfine` mean over 20 runs (sub-ms fixtures are exec-startup dominated, only `fib_rec` is compute-bound) |

A ratio of `100%` means strictly mov-only in `.text`. After stage 7d
the llvm-mov column hovers around 97–99 % across the fixture set, with
the only non-mov mnemonics being `call int jmp` — `call`/`int 0x80`
in `_start.s` (the runtime escape, gate-accepted) and `jmp` from the
7c1 dispatcher + 7d1 return-jmp + 7d3 call-jmp.

For comparison, `clang -O0..-O3` lands at 12–40 % mov ratio (ordinary
arithmetic / branches dominate; movs are a minority).

## Headline numbers

`fib_rec` is the only compute-bound fixture (the rest are sub-ms and
exec-startup dominated). On `fib(24)` the four-way comparison comes
out to:

| backend     | `.text` | mov %  | runtime |
|-------------|--------:|-------:|--------:|
| llvm-mov    | 3513    | 98.8 % |   87 ms |
| movfuscator | 12208   | 99.9 % | 1496 ms |
| clang -O0   | 156     | 38.9 % |  3.8 ms |
| clang -O3   | 129     | 12.3 % | 0.47 ms |

So llvm-mov is **~17× faster than movfuscator** on the same
mov-only workload (the headline ratio worth highlighting), but
**~23× slower than clang -O0** and **~185× slower than clang -O3** —
which is the cost of the mov-only constraint and worth being honest
about.

## Usage

```sh
make bench                            # regenerate bench/results.md
./bench/run.sh return0 return42 …     # specific fixtures
make bench-check                      # CI: regression-check vs committed baseline
```

Prerequisites: `make build` (for `bin/llvm-mov-llc`),
`make -C ../movfuscator-wasm setup build-native` (for `movcc`),
`clang-22` on PATH (for clang -O0..-O3 + the llvm-mov front-half),
`cargo` + `rustup target add i686-unknown-linux-gnu` (for Rust
fixtures), and `hyperfine` on PATH (for the runtime row).

## As a regression test

`bench/results.md` is **committed** and `make bench-check` re-runs the
bench, diffs against the committed numbers, and fails on any
divergence — but only in the **llvm-mov column**: `.text` / `.rodata`
size, mov count / total, and the non-mov mnemonic set.

Everything else is excluded, because none of it is reproducible on a
machine other than the one that last wrote the baseline:

- the generation timestamp and the runtime row (obviously host-dependent);
- the `total ELF (bytes)` row — dominated by the host's CRT / libc /
  rust-std, not by our output, which `.text` / `.rodata` already measure;
- every **reference column** (movfuscator, clang/rustc -O0..-O3). The
  host's gas/ld minor version moves the movfuscator number, and a
  different build of the same clang release moves the rest (Arch and
  apt.llvm.org clang-22 disagree on whether a `nop` is emitted).

The llvm-mov column is kept reproducible by
[`examples/rust/rust-toolchain.toml`](../examples/rust/rust-toolchain.toml):
a dependency that doesn't round-trip through `llvm-mov-llc` is linked
from rustc's own objects, so rustc's version would otherwise leak into
the `.text` we measure.

`make bench-check` is wired into CI alongside the test gates, so any
silent codegen regression (or unintended growth in `.text`/`.rodata`/
mov count) blocks the PR with a diff:

```
bench-check: drift detected vs committed baseline

@@ -14,7 +14,7 @@
 | metric | llvm-mov | <movfuscator> | clang -O0 | clang -O1 | clang -O2 | clang -O3 |
 |---|---:|---:|---:|---:|---:|---:|
-| .text size | 3513 | <movfuscator> | 156 | 113 | 129 | 129 |
+| .text size | 3617 | <movfuscator> | 156 | 113 | 129 | 129 |
```

When the change IS intentional (an optimisation, or a deliberately
larger codegen shape), the developer regenerates the baseline:

```sh
make bench
git add bench/results.md
```

and commits it alongside the implementation. The PR diff then shows
exactly what changed — every `mov` shaved off a byte-chain rewrite,
every byte trimmed from `.text`, shows up in the bench delta. This
makes mov-count and binary-size optimisations a first-class,
reviewable concern.

## Future work

- Multi-file fixtures (e.g. the AES test under
  `movfuscator-wasm/vendor/movfuscator/validation/crypto-algorithms/`)
  need linker-side support — the runner currently compiles one
  source file per fixture. A real compute-heavy crypto fixture
  would surface mov-only behaviour on a wider IR shape than the
  recursive-fib stress test.
